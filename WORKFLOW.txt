GO WITH THE FLOW
Beginner Workflow Guide
=======================

This project is a browser-only debate planner. It does not use a backend server or database.
Everything is saved in the browser with localStorage, and the current screen / round is tracked
with sessionStorage.

The app is built around one idea:
- A user creates a debate round.
- The round has two cases: Aff and Neg.
- Each case is made of contentions.
- Each contention has supporting points.
- Some points are main points; others are replies.
- Evidence can be attached to notes.
- The user can write crossfire notes and export a PDF/print version.


1) Main screens and what they do
=================================

1.1 index.html  -> Home screen
- Purpose: manage saved rounds.
- Responsibilities:
  * show all saved rounds
  * search rounds by title/topic/tournament/opponent
  * create a new round
  * rename a round
  * delete a round
  * open an existing round
- JS file: js/index.js
- This screen is for navigation and round management, not debate writing itself.

1.2 workspace.html -> Debate flow sheet
- Purpose: write and organize the actual round.
- Responsibilities:
  * switch between Aff Flow and Neg Flow
  * create and edit contentions
  * add main points and replies
  * show speech columns (constructive, rebuttal, summary, final)
  * attach evidence to a point
  * run timer
  * save automatically
- JS file: js/workspace.js
- This is the main working screen.

1.3 notes.html -> Crossfire notes screen
- Purpose: capture notes that happen outside the main flow chart.
- Responsibilities:
  * track first crossfire, second crossfire, grand crossfire, reflections
  * save note content as the user types
  * update the round title and side info
- JS file: js/notes.js

1.4 preflows.html -> Reusable pre-write screen
- Purpose: save reusable topic/side templates called preflows.
- Responsibilities:
  * create a preflow
  * edit a preflow
  * delete a preflow
  * open a preflow as a starting structure for a round
- JS file: js/preflows.js

1.5 common.js -> shared logic for all screens
- Purpose: the core engine of the app.
- This file builds the round data model, saves data, creates timers, handles DOM helpers,
  and defines the rendering logic used by all pages.


2) How the app starts
=====================

When a page loads:
1. The HTML is parsed.
2. CSS is loaded.
3. Scripts are loaded.
4. The script order is important:
   - js/common.js
   - page-specific script: js/index.js / js/workspace.js / js/notes.js / js/preflows.js
5. common.js immediately runs:
   - loadSavedData() reads saved browser data
   - db is created from localStorage
   - state is created as the live UI session object
   - startApp() runs to initialize the page

Important idea:
- db = saved data
- state = current in-memory view of what the user is doing now

Example:
- db.rounds stores the full saved rounds.
- state.round stores the round currently open on-screen.


3) Data storage model
=====================

The app keeps two main storage layers:

3.1 localStorage
- Used for permanent saved app data.
- Key names are:
  * goWithTheFlow
  * goWithTheFlowBackup
- This stores:
  * all rounds
  * all preflows
  * user settings
  * last selected round

3.2 sessionStorage
- Used for temporary current-session info.
- Examples:
  * open round id
  * current case side
  * jump-to-contention target
  * focus target note
  * open evidence panel


4) Main data objects
=====================

4.1 Round object
A round is the main debate record. It contains:
- id
- title
- topic
- tournament
- roundLabel
- opponent
- yourSide (pro / con / observer)
- firstSide (pro / con)
- createdAt / updatedAt
- cases
- contentions
- notes
- evidence
- crossNotes
- timers
- scroll state

A round always has two cases:
- pro
- con

Each case has a list of contentionIds.

4.2 Contention
A contention is a major argument block, such as:
- "Need for policy change"
- "Cost concerns"
- "Education benefits"

A contention keeps:
- id
- name
- startingPointIds

startingPointIds holds the top-level point ids that belong to that contention.

4.3 Note
A note is a point or reply card inside a contention. Each note has:
- id
- contentionId
- speechId
- parentId
- order
- text
- html
- marker
- evidenceId

speechId tells which speech column it belongs to, for example:
- pro-constructive
- con-rebuttal
- pro-summary

parentId means "this note is a reply to that note".
If parentId is null, it is a starting point.

4.4 Evidence
Evidence is one attached research item for a point.
It stores:
- id
- noteId
- html
- plain

This allows the user to paste evidence and keep it attached to a specific point.


5) Screen-by-screen workflow
===========================

5.1 Home screen workflow
File: index.html + js/index.js

How it works:
- The page renders a list of rounds from db.rounds.
- Each card shows:
  * title
  * side
  * tournament / round info
  * topic
  * last edit time
- Search filters the list by title/topic/tournament/opponent.
- Clicking Open loads the selected round into state.round and sends the user to workspace.html.
- Clicking New round opens a popup form with:
  * topic
  * tournament
  * round number
  * opponent
  * your side
  * first speaking side
  * starting preflow
- `createRoundFromForm()` builds a new round with `createNewRound()`.
- `saveToLocalStorage(db)` saves it in the browser.

The central functions here are:
- loadPreflowDropdown()
- openNewRoundModal()
- createRoundFromForm()
- displayRoundsList()


5.2 Workspace screen workflow
File: workspace.html + js/workspace.js + common.js

This is the main debate board.

The page is laid out like a debate flow sheet:
- left sidebar with case buttons
- title bar with timer and save status
- toolbar with undo/redo/font actions
- center flow paper with speech columns
- evidence panel on the right

When a round opens:
- `openRound(id)` loads the round from the saved data into state.round
- `renderWorkspace()` runs
- `buildFlowSheet()` clears and redraws the flow paper
- `calculateCaseFlowLayout()` decides where each point sits in the board
- `renderPointCard()` creates the visual card for each note
- `measurePointHeights()` computes height of cards
- `applyPointPositions()` places cards on the canvas

This is where the actual debate logic exists.

Core functions:
- addMainPoint(round, contentionId, speechId, text)
- addReplyPoint(round, parentId, speechId, text)
- addContention(round, caseSide)
- deletePoint(round, noteId)
- openPointActionsMenu()
- switchDebateSide()
- saveRoundAfterAMoment()

The points are not stored in one flat array. They are stored in a map like:
- round.notes[note.id] = note

That makes it easy to:
- find any note by id
- attach evidence to a note
- move a note under a parent reply
- rebuild the board from the current data


5.3 Notes screen workflow
File: notes.html + js/notes.js

This page is simpler than the workspace.
It does not draw the flow board. It only stores crossfire notes and round metadata.

`renderCrossfireNotes()` reads from `state.round.crossNotes` and fills the four textareas:
- firstCrossfire
- secondCrossfire
- grandCrossfire
- reflections

The listener on input automatically updates the round object and saves after a short delay.
This page is mainly about reflection and after-round analysis.


5.4 Preflow screen workflow
File: preflows.html + js/preflows.js

A preflow is a reusable opening structure.
It is not a full debate round, but a saved argument skeleton.

A preflow contains:
- title
- topic
- side (Aff or Neg)
- contentions
- notes
- evidence

When a user creates a preflow, it is stored in db.preflows.
Later, when creating a round, the dropdown can load a preflow as the starting structure.

This lets a debater re-use a prior argument set rather than building from zero.


6) How the flow board is laid out
=================================

This is the most important visual logic in the app.

The app uses these helper functions:
- getSpeechesForSide(round, caseSide)
- getSpeechesAfter(round, caseSide, speechId)
- getReplyPoints(round, parentId, speechId)
- calculateSpaceForPoint(round, note, caseSide, heights, saved)
- calculatePointPosition(round, note, top, caseSide, heights, saved, positions)
- calculateCaseFlowLayout(round, caseSide, heights)

Why this matters:
- The board has columns by speech type.
- A parent point may have replies in later speeches.
- Replies need to be stacked under the right parent card.
- The app must compute their vertical placement so the cards do not overlap.

The flow board is a visual tree:
- top-level note = root of a chain
- reply note = child under a parent
- replies can continue into later speeches
- the layout engine calculates spacing recursively

This is where the app becomes more than a text editor. It is a debate mapping engine.


7) Saving and auto-save logic
=============================

This project auto-saves often.

Main save flow:
- user edits a note / title / timer / crossfire field
- `saveRoundAfterAMoment(false)` starts a short delay
- after ~450ms, `saveThisRound()` writes the object
- `saveToLocalStorage(db)` writes to browser storage

The save system is defensive:
- if storage is full, the app shows a warning
- if save data is corrupted, it tries the backup key
- if both fail, it restores defaults

`db` is not restored from a server; it is loaded from localStorage on page load.


8) Timer logic
==============

The app includes a speech timer and prep timer.

Relevant ideas:
- `getTimerSteps(firstSide, durations)` defines the standard sequence of speeches.
- `createNewTimer(firstSide, durations)` creates working timer state.
- `startOrPauseTimer()` starts or pauses the active timer.
- `resetSimpleTimer()` resets the currently visible timer.
- `updateTimerButton()` updates the visible label.

The timer keeps track of:
- remainingMs
- prepLeft
- deadline
- running
- mode

This means it can stop cleanly when the tab closes or the app is reopened.


9) Evidence logic
=================

Evidence is used like this:
- the user clicks the clip button on a note
- that note gets an evidence panel opened
- the user pastes copied text or formatted content
- `cleanPastedHtml()` removes unsafe formatting and keeps readable HTML
- the evidence is attached to the note with evidenceId
- the note card shows a clip badge

This is handled in the common.js paste/cleaning utilities and in workspace.js rendering.


10) Where the unused helper was used
=====================================

The earlier helper `calculateContentionLayout()` was not connected to the real render flow.
It was not used by any call site in the app.

The actual active layout path is:
- `renderWorkspace()`
  -> `buildFlowSheet()`
  -> `calculateCaseFlowLayout()`
  -> `renderPointCard()`

So the real layout logic used by the app is the case layout function, not `calculateContentionLayout`.
The removed helper was effectively dead code.

This is why the app still works normally after its removal: the live screen depended on the active layout engine instead of the unused helper.


11) Simple beginner summary
==========================

Think of the project as a debate planning board:

- Home page = round library
- Preflows page = reusable argument outlines
- Workspace page = the actual debate map
- Notes page = reflection and crossfire notes
- common.js = core logic and data engine
- HTML files = screens
- JS files = behavior and rendering

The project is not a traditional app with a backend.
It is a single-page browser app that stores everything locally and redraws the interface based on state.

A beginner can understand it by following this path:
1. create a round
2. add contentions
3. add main points
4. add replies
5. attach evidence
6. save automatically
7. switch sides
8. edit notes and export PDF

That is the whole project lifecycle.
